# 일정 추출 보완 (11/6)

기준: 프런트 `integration/b-d`의 `27da29e`. 실제 제안 CSV에서 모든 팀원의 가능 시간이 비어 있고 불가 시간만 저장된 상태를 확인했다. 일부 불가 구간의 12:00·18:00은 보존돼 있으므로 모든 시각을 자정으로 자르는 공통 저장 버그로 단정하지 않는다.

## 변경

- `src/server/b/schedule-time-rules.ts`: 검색 기간의 서울 날짜·요일 달력과 해석 규칙. 반복 요일, 구체적 시각, 명시적인 ‘나머지 전부 가능’, 여러 메시지의 조건 결합을 안내한다. 불가만 말한 경우 가능한 시간을 임의로 만들지 않는다. 모호한 수업 종료 시각은 회의 참석 가능으로 확정하지 않는다.
- `src/server/b/extractor.ts`: 위 규칙을 일정 추출 프롬프트에 추가한다. B 계약과 SQL 필드는 바꾸지 않는다.
- `src/server/normalize-schedule-output.ts`: 기존 보정 로직을 외부 API 없이 검증할 수 있도록 옮겼다. 시간 반올림 → 출발지 누락 보완 → 검색 기간 자르기 → 겹친 불가 구간 빼기 순서는 유지한다.
- `src/server/gemini-generate.ts`: 보정 전후 팀원별 슬롯 수·총 분량을 Vercel 서버 로그에 기록한다. 메시지 원문·주소·시각·팀원 ID는 기록하지 않는다. 추가 AI 호출이나 자동 재시도는 없다.

## 확인

`npm run test:schedule-extraction` 4개, `npm run test:c` 15개, `npm run typecheck`를 통과했다. 새 테스트는 명시적인 18~22시 보존, 불가와 겹친 구간만 제거, 목요일 및 나머지 요일 가능 시간이 C까지 전달되는 경로를 확인한다. AI 응답은 통제된 테스트 데이터이므로 실제 Gemini의 자연어 이해 성공을 입증하는 테스트는 아니다.

## 통합과 실제 확인

이 브랜치의 변경만 현재 프런트 작업에 병합한다. 이전 C 폴더나 프런트 전체를 덮어쓰지 않는다. SQL 변경과 Supabase migration은 필요 없다. 기존 제안 조건도 자동 변경하지 않는다.

배포 뒤 같은 대화와 11/9~11/16 검색 기간으로 새 제안을 만든다. 목요일 가능 시간, 월·수 18~22시 불가, ‘월화수 외 나머지 가능’이 각 발화자에게 반영됐는지 확인한다. 모호한 수업 종료 시각은 확정된 가능 시간으로 오해하지 않아야 한다.

`[scheduling] time normalization` 로그에서 보정 전부터 가능 시간이 0이면 B 입력/추출을, 보정 후에만 감소하면 기간 자르기·불가 겹침을 조사한다. 이 로그만으로 어떤 자연어 진술이 틀렸는지까지 판단할 수는 없다.
